# AresOS — Дорожная карта

**Цель проекта:** 64-битная ОС «голого железа» (x86-64) на C + NASM с собственным
UEFI-загрузчиком, которая в финале запускает Windows-приложения формата PE (.exe)
через собственный слой совместимости WinAPI (подход, как у Wine/ReactOS, но «снизу»).

**Честная оценка:** полноценный запуск любых Windows-программ — это уровень Wine
(30+ лет разработки командой). Наш реалистичный ориентир: сначала **консольные
.exe** (hello world, скомпилированный MinGW), затем последовательное расширение
API. Каждый этап ниже — рабочая, проверяемая версия ОС.

## M1. UEFI-загрузчик + ядро-пустышка
_Примерно 1–2 недели_

- UEFI-приложение (`BOOTX64.EFI`) на C через POSIX-UEFI/gnu-efi:
  - инициализация консоли, вывод строки;
  - чтение `KERNEL.ELF` с ESP-раздела (FAT32) через UEFI File Protocol;
  - парсинг ELF64, загрузка сегментов;
  - получение карты памяти (`GetMemoryMap`), настройка видеорежима через GOP
    (Graphics Output Protocol) — получаем framebuffer;
  - `ExitBootServices()` и прыжок на точку входа ядра.
- Ядро-пустышка: входная точка на NASM → `kmain()` на C → зависание (`hlt`).
- `Makefile`: сборка ядра, загрузчика, FAT32-образа через `mtools`, запуск в QEMU+OVMF.
- Linker script для ядра.

**DoD:** `make run` → в окне QEMU видно строку `AresOS kernel loaded`, которую вывело **ядро** (не загрузчик).

## M2. Диагностика ядра
_1–2 недели_

- Serial port COM1 (порт 0x3F8) — лог ядра в терминал (`-serial stdio`).
  Это главный инструмент отладки навсегда.
- `kprintf()` (свой мини-printf: `%s %d %x %p`).
- Вывод текста в framebuffer (свой 8x16 шрифт) — консоль ОС.
- GDT (минимум для long mode), **IDT**: обработчики исключений CPU
  (#GP, #PF, #UD...) с дампом регистров + стек-трейс. Kernel panic.

**DoD:** искусственный `#PF` (записали по нулевому указателю) красиво печатает
причину и регистры на экран и в serial вместо мёртвого зависания. Подключён GDB (`make debug`).

## M3. Управление памятью
_2–4 недели. Сердце ОС._

- **PMM** (physical memory manager): битовая карта страниц 4 КиБ по карте памяти от UEFI.
- **VMM**: свои таблицы страниц; **higher-half ядро** (`0xFFFFFFFF80000000`);
  прямое отображение всей физпамяти (HHDM) **2-МиБ страницами** ← первая настоящая оптимизация.
- Kernel heap: `kmalloc/kfree` (slab-аллокатор).

**DoD:** streсc-тест аллокатора (миллион случайных alloc/free) без утечек и паник.

## M4. Прерывания и время
_2–3 недели_

- APIC/x2APIC + IOAPIC (вместо legacy PIC), MSI позже.
- LAPIC-таймер (калибровка по HPET/TSC) → системный тик.
- Клавиатура PS/2 (прерывания, scancode → ASCII).
- `rdtsc`-таймеры для профилирования.

**DoD:** ядро реагирует на клавиши, показывает uptime с точностью таймера.

## M5. Многозадачность
_3–6 недель_

- Kernel threads: контекст на NASM (сохранение регистров, `FXSAVE` для FPU/SSE),
  планировщик round-robin → приоритеты.
- Spinlock/mutex (с `pause` в цикле ожидания), per-CPU данные. SMP (все ядра CPU) — по желанию, но сразу закладываем в дизайн.

**DoD:** два+ потока параллельно пишут в консоль, нет гонок; нагрузка распределяется.

## M6. Диск и файловая система
_3–5 недель_

- Драйвер диска: AHCI (SATA) — стандартный путь; (вариант проще на старте: initrd-образ, загруженный загрузчиком в RAM).
- **VFS** — виртуальная ФС: единый интерфейс open/read/write/readdir.
- **FAT32** (чтение+запись) поверх VFS. NTFS — только чтение, намного позже.

**DoD:** ядро монтирует диск, `cat /readme.txt` в нашей консоли читает файл с реального образа.

## M7. Пользовательский режим
_4–8 недель_

- Ring 3: TSS, переключение в user mode.
- Syscall-интерфейс: инструкция `syscall/sysret` (не int 0x80 — быстрее).
- Загрузчик **ELF**-программ AresOS, мини-libc, shell.
- Изоляция адресных пространств процессов (каждому — свои таблицы страниц).

**DoD:** shell запускает `hello.elf` как отдельный процесс; краш процесса не роняет ядро.

## M8. Подсистема PE / WinAPI — «Долгая дорога»
_Постоянный этап, начинается когда стабилен M7_

1. **PE loader** (по Microsoft PE/COFF Specification):
   парсинг заголовков DOS/NT, маппинг секций (.text, .data, .rdata) по виртуальным
   адресам, ImageBase, **релокации** (.reloc), таблица импортов (IAT).
2. **kernel32/ntdll-совместимость** — наша реализация:
   - минимум для консольного hello.exe (MinGW): `GetStdHandle`, `WriteConsoleA`,
     `ExitProcess`, `VirtualAlloc/VirtualFree`, `HeapAlloc`, `GetLastError`...;
   - TEB/PEB-структуры, SEH позже.
3. Тестовый стенд: `x86_64-w64-mingw32-gcc hello.c -o hello.exe` → AresOS его запускает.
4. Расширение API-сета → файлы, потоки (CreateThread), DLL → user32/gdi32-стыбы →
   собственная графическая подсистема.

**DoD этапа 1–3:** `hello.exe`, собранный под Windows x64, печатает текст в консоли AresOS.

нельзя** — изучаем идеи и пишем своё по документации Microsoft Learn и PE/COFF spec.
